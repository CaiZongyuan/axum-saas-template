# 跟做：桌面壳资源长测

[上一章](./25-load-reports.md)观察的是服务端在负载下的吞吐、饱和与队列走势；本章把镜头转向另一端——[Electron 安全壳](./20-electron-shell.md)里的渲染进程。桌面应用最容易拖慢的不是哪一次点击，而是"开一整天"：DOM 越挂越多、监听器越积越攒、内存缓缓爬升。桌面长测用真实的壳与真实的共享页面回答一个问题：**循环使用一小时后，渲染进程的资源曲线长什么样**。它和负载报告一样守三条规矩：只压一次性栈；只在夜跑与版本发布时产出、永远不进普通 PR 门禁；增长观察只描述趋势——**单次长测不构成泄漏结论**。

## 1. 压的是临时栈，开的是干净壳

[desktop-soak.mjs](../../scripts/perf/desktop-soak.mjs) 复用桌面冒烟那套一次性栈：测试版 PostgreSQL、Redis、RustFS、Mailpit 全部以独立容器拉起，API 与 Web 开发服务绑定空闲端口，跑完随容器销毁——你的开发数据不会被碰到。栈上限流连同 Redis 降级兜底一起放宽：浏览循环每分钟要打几百次会话与列表请求，长测观察的是渲染进程，不是限流；与[受控负载栈](./25-load-reports.md)同一套理由。[fixtures.mjs](../../scripts/perf/fixtures.mjs) 经公开 HTTP 接口播种受控数据（默认 6 用户 × 8 文档、部分带附件）。

壳本身以测试用户目录启动（`SAAS_DESKTOP_USER_DATA_DIR` 指向一次性目录），登录、浏览、上传下载、开关弹窗全部走[真实共享页面](./20-electron-shell.md)——桌面长测不注入任何测试桩到页面里，它模拟的就是一个真实用户在开开关关。知识库示例移除后，浏览场景没有页面可走，命令会在开工前诚实说明并退出（与负载命令同一套模式），报告整形与本章记载的做法照常可用（见 §5 的删例边界）。

## 2. 场景与采集：指标从哪来

循环的每一步都是用户的真实动作：从文档列表打开一篇文档 → 刷新附件面板 → 面板里有附件就点一次下载 → 上传一份本轮唯一的附件、确认其出现在列表后**随即删除** → 打开"删除文档"确认弹窗再取消 → 采样 → 返回列表，换下一篇继续。上传、下载、删除三个附件动作都走真实的哈希、进度与存储往返，但"传后即删"让数据集保持**平稳**——循环不能一边给页面添料一边观察"页面有没有变大"，否则测的是自己制造的增量，不是壳的趋势。采样点落在**文档详情页亮着、弹窗刚关**的时刻——这是循环里最重的一屏（Markdown 预览、导出面板、附件面板同时在册）。

| 指标             | 采集方式                                                                        | 读法                      |
| ---------------- | ------------------------------------------------------------------------------- | ------------------------- |
| `rendererRssKiB` | 主进程 `app.getAppMetrics()` 里渲染进程（Electron 44 记作 `Tab`）的 working set | 进程真实内存占用          |
| `heapKiB`        | 渲染进程 `performance.memory.usedJSHeapSize`                                    | JS 堆，波动随页面切换正常 |
| `domNodes`       | `document.getElementsByTagName('*').length`                                     | 详情页在册节点数          |
| `listeners`      | 初始化脚本包裹 `EventTarget` 计数的**净注册数**（仅长命目标）                   | 监听器压力的代理指标      |

监听器计数值得展开说：只统计**长命目标**——`window`、`document`、`body`、根容器——监听器泄漏恰恰积累在这些地方；挂在短命目标（每次请求的 AbortSignal、随手创建的元素）上的注册会随目标一起被回收，对身份计数器只是噪声，按构造排除。包裹层按"目标 + 类型 + 捕获阶段"去重（和 DOM 语义一致），`once` 监听器在触发后出账，随 `AbortSignal` 注册的监听器在信号中止时出账。它是长命目标上 EventTarget API 用量的代理，不是穷举审计——够看出"越积越多"的趋势，不该被当成精确清册。

预热（默认 15 秒，`DESKTOP_SOAK_WARMUP_SECS`）让首屏、水合与路由级懒加载块先稳定，序列从稳态起步而不是从冷启动起步。报告同时记录预热时长、采样时长、采样间隔与运行版本（git SHA、desktop 包版本、Electron 版本）。

## 3. 报告怎么读：时间序列与增长观察

每条命令写 `.scratch/perf/desktop-soak-report.json`：

- **原始时间序列**：每个采样点的四项指标全量保留——趋势可疑时，能回到具体时间点看现场。
- **聚合**：各指标的 min / avg / max。
- **增长观察**（`growthNotes`）：把序列按首末四分位对比，某指标末四分位中位数比首四分位高出 25% 时记一条观察。观察的措辞是"本次运行观察到增长，建议复跑确认"——**复跑确认是流程的一部分，不是客套话**：单次长测里一次 GC 暂停、一次后台任务都可能制造假象，连续几轮同向增长才值得开 issue。

增长观察永远不改变命令退出码——它是报告材料，不是门禁。

## 4. 在哪跑、怎么调

```bash
just perf-desktop-soak
```

前置只有 `pnpm install`（壳的 Electron 首次 require 时才下载二进制，命令会先自举）与显示器或 xvfb。栈、壳、数据目录全部自动管理，容器跑完即毁：

| 变量                         | 默认   | 作用                       |
| ---------------------------- | ------ | -------------------------- |
| `DESKTOP_SOAK_DURATION_SECS` | `300`  | 循环时长（秒，不含预热）   |
| `DESKTOP_SOAK_WARMUP_SECS`   | `15`   | 预热时长（秒）             |
| `DESKTOP_SOAK_SAMPLE_MS`     | `2000` | 采样间隔（毫秒）           |
| `PERF_SCALE`                 | `sm`   | 播种规模档（sm / md / lg） |

[perf-nightly.yml](../../.github/workflows/perf-nightly.yml) 在夜跑（与手动、发布触发）时带 xvfb 跑桌面长测，报告 artifact 保留 30 天。普通 PR 永远不跑它——PR 上只有[确定性门禁](./24-perf-gates.md)。

## 5. 基线实测与删例后的去处

基线留档如下（本地 x86_64 WSL2，默认档 sm 规模、300 秒循环、2 秒采样；数字随机器浮动——留档给后来者一个对比起点，不是任何机器上的承诺）：

| 指标             | min–max               | 首四分位中位 | 末四分位中位 | 增长观察 |
| ---------------- | --------------------- | ------------ | ------------ | -------- |
| `rendererRssKiB` | 256 772 – 461 248 KiB | 313 980      | 453 192      | +44.3%   |
| `heapKiB`        | 44 253 – 88 200 KiB   | 56 213       | 71 623       | +27.4%   |
| `domNodes`       | 61 – 74               | —            | —            | 无       |
| `listeners`      | 293 – 295             | —            | —            | 无       |

（Electron 44.4.5；环境见上文。）按 §3 的读法：本轮四项指标里，监听器全程钉在 293–295、DOM 节点在 61–74 之间随页面切换往返——这两条平的曲线正是"循环没有在积累东西"的直接证据。RSS 与 JS 堆触发了增长观察，看形状：堆在 44–88 MiB 之间随 GC 往返、不单调；RSS 则从约 250 MB 缓慢棘轮式爬到约 460 MB——上传下载循环带来持续的分配噪声，在没有内存压力时分配器不会急着归还物理页，这个形态**描述**了本轮的行为，但不足以**断言**任何趋势。按规矩，下一步是同一台机器上背靠背复跑：若每一轮的起点都稳定在 250 MB 上下，爬升就是轮内分配行为；若起点逐轮抬高，跨轮积累才值得开 issue。完整报告（含原始时间序列与运行版本）由命令写入 `.scratch/perf/desktop-soak-report.json`，不入版本库。

删例边界与[负载报告](./25-load-reports.md)同一条线：浏览场景以知识库示例的共享页面为载体，场景与采集代码（`tests/desktop/soak.spec.ts`、`scripts/perf/desktop-soak.mjs`）都登记在示例所有权清单里，示例移除时随之删除，`just perf-desktop-soak` 会在开工前诚实说明并退出。留下的是两样东西：业务无关的纯报告整形——[desktop-report.mjs](../../scripts/perf/desktop-report.mjs) 的聚合与增长观察，不在清单内、删例后照常可用；以及本章记载的做法本身——监听器净计数只算长命目标、主进程 `getAppMetrics()` 读渲染进程、采样点落在最重的一屏、增长观察不复跑不下结论。为自己的桌面应用建模时，以这些语义为模板重建你的采集与场景。

## 6. 运行本章检查

```bash
DESKTOP_SOAK_DURATION_SECS=25 just perf-desktop-soak  # 短循环先验收链路，再跑长测
just perf-desktop-soak          # 任一轮长测跑通即验证本章链路
just check                      # 主门禁不包含桌面长测——这正是设计
```

采集与报告的确定性部分（聚合、增长观察的判定边界）由 `tests/tooling/desktop-soak-report.test.mjs` 随 `just check` 验收；壳冒烟（`just desktop-smoke`）保证长测所驱动的页面与选择器在 CI 里真实可用。
