## 成功标准

开发者从一份模板出发，能够实现自己的 Rust 业务模块和 API，复用 SaaS Core，写出行为测试并部署。每个阶段可以编译、请求、观察并继续修改上一阶段的代码。

- 后端开发路径包含模块、数据模型、迁移、请求/响应、用例、认证、授权、事务、错误、测试和部署。
- 连续案例逐章新增代码，明确文件、接入点、前章状态、完整变更、命令、响应与失败检查。
- 初次运行以 HTTP 健康与数据库结果验收；从这里直接进入创建自己的业务。
- 有经验的开发者能按主题直接查找开发指南和 Core 公共接口。
- API 与配置来自实际实现；教程区分已存在的框架能力、当前参考业务与读者将新增的案例能力。
- 双语、旧发布路径、同页语言切换、搜索和自定义 base 继续有效。
- 示例专有源码和文档有明确所有权；删例后 Core 文档仍可构建。
- 文档、代码示例、真实 HTTP 行为与浏览器阅读体验有各自的验证证据。

## 参考站的借鉴方式

Project Structure 同时解释目录、增加模块的步骤和请求数据流。Endpoints 用一个 Widget 模块串联模型、输入输出、用例、路由、挂载、迁移和 curl 结果。Development 把日常开发与按主题的指南连起来；Testing 和 Production 将同一业务带到验证与交付。

借鉴这种“开发任务 → 源码位置 → 最小实现 → 请求验证 → 失败检查”的结构。Dougong 的实际接口来自 Rust workspace、Axum、SQLx 和已有 Core；Python 的分层目录、模型发现、依赖注入或任务注册方式不作为本仓库规范。

研究证据、页面链接和参考站自身的一致性问题集中在 [研究记录](../research/backend-documentation-reference.md)，正式文档按本仓库源码核实。

## 贯穿案例：新增工单后端

工单是读者将新增的教学业务，尚未存在于当前默认应用中；当前模板仍以知识库作为完整、可移除的参考业务，便签用于证明组合合同。

工单用最少业务对象串联框架：用户创建工单、查询与修改，资源规则控制访问，业务与审计共同提交，附件和导出接入公共文件与任务能力。

| 阶段               | 开发改动                                    | 新增理解                         | 可观察成果                                  |
| ------------------ | ------------------------------------------- | -------------------------------- | ------------------------------------------- |
| 1. 创建模块        | Rust 模块、声明、Router、OpenAPI、组装点    | 业务与 Core 的依赖方向           | 静态开发接口返回 JSON、request_id，合同可查 |
| 2. 持久化模型      | 自有 schema、SQL 迁移与 module.json         | 表所有权、约束、SQLx 查询        | 迁移成功，readiness 与源码一致              |
| 3. 定义协议        | 请求/响应 DTO、BoundedJson 与 Domain 校验   | 协议、规则与存储的职责           | 无效输入得到统一错误                        |
| 4. 接入身份与授权  | require_session、有效成员检查、工单资源策略 | 认证与资源授权                   | 匿名、无权和有权请求结果明确                |
| 5. 实现业务用例    | 工单创建/查询/更新、事务与 audit::append    | 跨模块公共接口、提交边界         | 创建后可读取；审计失败回滚业务              |
| 6. 保护重试与并发  | 幂等 claim/complete、预期版本               | 重放和乐观并发                   | 相同请求只写一次，旧版本冲突                |
| 7. 接入文件        | 文件归属、候选对象、核验与发布              | PostgreSQL 与对象存储一致性      | 附件上传下载正确，越权拒绝                  |
| 8. 接入后台执行    | 业务快照、Job、Handler 注册与通知意图       | 请求/Worker 生命周期、租约和终态 | 可查询导出结果，重试历史与通知一致          |
| 9. 验证并生成合同  | 随各阶段交付的 HTTP 测试、最终合同/SDK 核对 | 公开行为测试与协议单一来源       | 业务检查与合同检查通过                      |
| 10. 部署自己的业务 | 生产配置、迁移、健康、观测、备份恢复断言    | 交付与运行责任                   | 独立环境可验证新增业务及其恢复              |

每章应提供完整的新增/替换代码或可执行变更，而不是让读者把省略号、没有定义的 helper 和未注册 Handler 拼成应用。讲解性片段明确上下文，并链接完整受检查版本。

源码案例以版本化教学副本或示例 fixture 维护，检查使用临时工作目录。教学代码在一条学习路径内演进，默认应用是否注册新示例作为单独的实施范围记录；文档重构不自动把工单承诺为新的默认产品功能。

测试随阶段交付：首次路由验证 JSON 与 OpenAPI，持久化验证读写，授权验证拒绝，事务验证回滚，任务验证发布和重试；最终课程验收检查这些阶段连贯。

## 项目结构页应回答的问题

1. 我自己的业务代码放在哪里？当前 Rust 模块如何提供公开能力？
2. HTTP 请求经过哪些实际层次？DTO、Domain 与 Application 各负责什么？
3. Core、Platform 和具体业务的依赖方向是什么？
4. 新增表、HTTP 路由、OpenAPI 或 Worker Handler，要改哪个显式组装点？
5. 业务测试、生成合同与示例所有权分别登记在哪里？
6. 一个最小模块完成后，怎样执行请求确认它已经工作？

小模块先保持简单，按实际复杂度拆出文件。当前知识库的 `domain.rs`、`application.rs` 和 `mod.rs` 是可查的实现依据；文档不要求为每项功能机械创建 Repository/Service 或更多抽象层。
