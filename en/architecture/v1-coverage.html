v1 capability coverage and acceptance ​

This page is v1's ledger: every row of the spec's §8.6 feature coverage matrix lands here as real links — run entries, source guides, online tutorials and verification map one to one, and the doc build's existence checks guard every link target (a missing source file fails the build), so tutorials and source never drift apart silently. The matrix records only delivered capabilities; design notes (such as spec §15.2's Mobile and the Outbox extension chapter) stay out of the matrix and carry no coverage marks — the documentation leaves no blanks to fill. Evidence for Core capabilities is written directly into the matrix and is guaranteed to hold after removing the examples.

Four reading paths ​

  1. Quick start: Quick start — toolchain, just dev, registering the first account, service status and failure scenarios.
  2. Follow the tutorials: start from the first full-stack request and work chapter by chapter; every chapter maps to real commands and tests.
  3. Build your own business: compose and remove reference examples — delete the knowledge-base example per the ownership manifest and Core keeps running as before.
  4. Verification and reference manuals: running tests and checks, Core and example boundaries, and the generated references (API contract, API configuration).

Acceptance summary ​

  • Default full stack: tutorials delivered ticket by ticket starting from the first full-stack request; daily gate just check, real browser journeys just e2e, milestone just check-full.
  • Electron: the secure shell tutorial + desktop smoke (just desktop-smoke, every PR in CI).
  • Mobile: not implemented and not planned for v1 (implementation ticket #22 recorded as not planned). Spec §15.2 and the testing strategy's Mobile entries stay as design notes and are not to be implemented from (the implementation decision follows #22; the divergence is intentional); no corresponding checks, no documentation blanks.
  • Performance: deterministic budgets are accepted every PR with just check (perf-ci); load/saturation/trajectory soak reports are produced only by perf-nightly (nightly, manual and release triggers), artifacts kept 30 days, never acting as a PR gate.
  • Backup and restore: backup and isolated-environment restore drill verifies documents, attachments and jobs on an isolated restore environment; the archive carries no secrets, and the drill cleans up credentials and certificates at the end.
  • Example removal: removing the examples executes per the ownership manifest; CI's example-removal job drills the whole thing every PR; after removal just check-core is green.
  • Generated references: the API contract is generated from OpenAPI (contracts:check guards drift), the configuration reference is generated from Settings and cross-checked against .env.example; the permission and job catalogs are carried by tutorial prose and have no generated reference yet — recorded honestly, not faked.

Release and reproduction ​

The site publishes at https://caizongyuan.github.io/axum-saas-template/, continuously updated with main; the "source version" in every page's footer is the repository commit that page's acceptance corresponds to, and the publish task verifies the built docs against the commit before going live. Full reproduction steps are in quick start. The v1 milestone verification command: just check-full.
