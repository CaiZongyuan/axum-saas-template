v1 capability coverage and acceptance ​

This page preserves v1 capability coverage and historical acceptance so maintainers can trace the specification, implementation and evidence from those revisions. Ticket states, measurements and acceptance versions below are historical records. Use Developer documentation for current learning paths and GitHub Issues for live implementation status. The matrix maps the spec's §8.6 feature coverage matrix to actual source and migrated guides.

Current development entries ​

  1. Start backend development: Quick start verifies startup and HTTP; project structure locates source.

  3. Verify and deliver: Feedback loop, production deployment and independent restore.
  4. Replace and look up: Remove reference business, Core/business boundaries, API contract and configuration.

Acceptance summary ​

  • Default full stack: tutorials delivered ticket by ticket starting from the first full-stack request; daily gate just check, real browser journeys just e2e, milestone just check-full.
  • Electron: the secure shell tutorial + desktop smoke (just desktop-smoke, every PR in CI).
  • Mobile: not implemented and not planned for v1 (implementation ticket #22 recorded as not planned). Spec §15.2 and the testing strategy's Mobile entries stay as design notes and are not to be implemented from (the implementation decision follows #22; the divergence is intentional); no corresponding checks, no documentation blanks.
  • Performance: deterministic budgets are accepted every PR with just check (perf-ci); load/saturation/trajectory soak reports are produced only by perf-nightly (nightly, manual and release triggers), artifacts kept 30 days, never acting as a PR gate.
  • Backup and restore: backup and isolated-environment restore drill verifies documents, attachments and jobs on an isolated restore environment; the archive carries no secrets, and the drill cleans up credentials and certificates at the end.
  • Example removal: removing the examples executes per the ownership manifest; CI's example-removal job drills the whole thing every PR; after removal just check-core is green.
  • Generated references: the API contract is generated from OpenAPI (contracts:check guards drift), the configuration reference is generated from Settings and cross-checked against .env.example; the permission and job catalogs are carried by tutorial prose and have no generated reference yet — recorded honestly, not faked.

UI and multi-example series acceptance (#57) ​

The whole UI series (UI01–UI15, parent #57) — all 61 user stories — was accepted on the integrated revision 4f971ed plus this ticket's acceptance repairs (the head commit of the corresponding PR):

  • Gates and journeys: just check, just check-full (12 specs, 15 real-browser journeys, including database pause/recovery, a real rate-limit window, two-browser session isolation, Worker crash recovery and a real object-storage failure retry) and just e2e-docs (public site zh/en × light/dark × narrow screens and base paths) all pass on this revision. The legacy-fallback contracts — unknown paths fall back to the universal home, and notifications stay readable with understandable unavailable feedback after the target business is removed — are covered by the app-shell and notification contract tests, while the post-deletion/revocation "no longer exists" feedback keeps running inside the e2e journeys.
  • Multi-example combinations: CI's example-removal job (every PR) drills, on the same revision, the dirty-copy refusal, dual → notes-only → core-only, an independent knowledge-only copy, and a new business joining through the public interfaces; every combination's gate (check-core, docs build, typecheck, frontend tests, web build, boundary check) passes. The desktop secure shell is verified by the desktop-smoke job (every PR).
  • Performance budgets: the only budget-baseline change in the series is UI05 adding the design-system showroom and the icon catalog to the lazy-loading baseline (a tightening); the 400/500 KiB first-load ceilings in perf-ci were never raised, and the showroom and icon catalog stay out of the first bundle.
  • Public pages: Landing, Documentation, Blog and Downloads — both languages, both themes, narrow-screen navigation, base paths, metadata and real CTAs — are covered by e2e-docs and the docs contract tests; Blog and Downloads clearly say "coming soon" instead of presenting placeholders as delivered.
  • Tutorials and migration cleanup: online chapters are bilingual per the published list (docs:check enforces registration and consistency); bilingual tutorials, example registration and behavior tests shipped with their implementation tickets, and post-removal bilingual trimming is verified by the example-removal job's docs build. The old-message/old-docs migration items and unwired legacy plumbing are cleared. One gap remains: tutorial 16 (Redis body cache with database fallback) never got its English translation inside the owning ticket's scope; it keeps an honest pending marker and is tracked in #96.
  • Acceptance repairs: the acceptance run exposed 7 early e2e journeys still assuming register/sign-in stays on the old home view and relying on the runner's default language (the UI04 device-language probe renders English). They now pin zh-CN following the existing password-reset pattern and assert the actual landing (register/sign-in enter the documents entry; the sign-out control lives on the universal home view). No new abstraction, no weakened assertion.
  • Story 61: this section is the acceptance record for "integrate the current v1 implementation and acceptance before the next round"; the next UI/site round starts from this revision.

Style-alignment round acceptance (UI-R1–R5, #99–#103) ​

After the first round merged, a second alignment round was executed and accepted ticket by ticket on the user's verified conclusion that the delivery's look and structure fell far short of the reference projects: tokens and component geometry (#104), the icon system entering the app (#105), the grouped settings layout (#106), shell slots and the single-mount layout route (#107), and the collapsed assembly default plus documentation/verification hygiene (#103). Gates and CI meet the same bar as round one (just check, just e2e-docs, and the verify/desktop-smoke/example-removal jobs); R5 extends the example-removal scenario into a five-combination drill that includes explicitly re-adding the notes example, and adds the in-app theme real-browser e2e (tests/e2e/theme.spec.ts). The gap analysis, per-ticket delivery and pixel-level before/after comparisons are recorded in the UI series handoff report; the design-side record lives in docs/ui/design.md §5, the alignment round.
