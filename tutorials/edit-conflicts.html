跟做：显式保存与版本冲突 ​

本章在上一章的安全预览上加入编辑。运行 just dev，打开自己的文档，点击“编辑文档”，修改标题或 Markdown，然后“保存文档”。成功后返回阅读页，版本递增；列表标题与正文缓存随之更新。

编辑器有两种布局：宽屏（≥1024px）时“编辑”与“预览”两栏并排，预览随输入实时刷新；窄屏时收拢为“编辑 / 预览”页签，与上一章一致。保存始终是显式动作——两种布局都不会替你保存。设计系统的“场景”页签里有“保存冲突与草稿保护”，用演示数据离线体验同一套保存反馈。

1. 先亲手制造一次冲突 ​

  1. 在两个浏览器标签页打开同一篇文档的编辑页，确认两边都显示“基于版本 1 编辑”。
  2. 在第一个标签页写“第一份修改”并保存，阅读页显示版本 2。
  3. 在第二个标签页写“第二份草稿”并保存。此时显示版本冲突，草稿保留。
  4. 点击“读取最新版本”，看到已保存的版本 2。编辑框仍是自己的草稿。
  5. 核对后选择“已核对，保留草稿并继续”，手动合并文字再保存；或者选择“放弃草稿，采用最新内容”。这两个选择都不会自动保存。

如果第三次修改又在你保存前提交，新保存仍会得到冲突。没有自动覆盖，也不把多人实时协同或历史版本浏览混入本章。

顺手拖一下窗口宽度：从宽屏拖到窄屏再拖回来，页签出现又消失，而正文和标题留在原处。两种布局渲染的是同一个编辑框，布局切换不重挂载面板，草稿因此不动。

2. 一次条件更新决定谁能成功 ​

更新 API使用 PUT /api/v1/knowledge/documents/{id}，请求包含 title / markdown / version。它沿用 Session、Origin、CSRF、输入上限与结构化错误。版本必须为正整数。

更新用例先锁定当前 Membership，再锁定 Knowledge Base 并检查 Grant。无权看文档返回 404，Reader 的写入返回 403。更新只在请求 version 等于数据库当前 version 时成功，同时递增 version、更新作者和时间。

sql
UPDATE knowledge.documents
SET title = $1, markdown = $2, version = version + 1
WHERE id = $3 AND version = $4;

这是并发控制的简化形状，完整代码还包含知识库归属、授权和审计。两个写入无需先读版本再在应用内比较：数据库条件更新保证它们不能同时覆盖同一版本。落后的保存返回 409 document.version_conflict。

文档修改和 Audit 在同一事务提交。审计失败会回滚正文和版本，修复后仍可用原版本重试。文档更新使用 version；创建时的幂等键不能替代并发控制。网络错误后不要自动盲目重发更新，读取最新版本并核对实际提交结果。

3. 草稿与服务器资源分开 ​

共享编辑界面复用创建表单、Markdown 预览和生成 SDK。Query 管理已保存资源；输入框与基准版本组成一次本地编辑会话。后台刷新可以更新 Query 中的服务器内容，但不会自动替换正在编辑的文本或基准版本。

布局由媒体查询选择，共享 View 提供 data-editor-layout="wide|narrow" 作为测试与样式的公开钩子。宽屏预览逐键实时刷新；正文无效（NUL 或超过 1 MiB）时保留上一次可用预览，错误在保存或切换页签时提示，不覆盖标题等其它输入错误。窄屏页签保持显式切换：切到“预览”先校验正文，无效则留在编辑页签并显示错误；页签支持方向键移动，与上一章的键盘路径一致。预览渲染是低优先级更新，长文输入不会阻塞键入。

冲突后再次保存先禁用，用户必须读取并核对最新内容。失败警告与冲突核对区块是编辑器与设计系统场景共用的组件——场景演示的正是线上行为。网络失败和冲突都保留输入。保存期间禁用写入控件，成功后更新相关列表与详情缓存；退出页面后的迟到响应不会把用户导航回来，身份变化后的旧响应也不能重新写入上一身份缓存。

4. 页面离开与浏览器刷新 ​

Web 导航适配使用 TanStack Router blocker。共享 View 只通知宿主草稿是否发生变化，不 import Router 或实现另一套 Web 页面。

站内离开显示“继续编辑 / 确认离开”对话框；浏览器刷新或关闭使用原生 beforeunload 提示，其文案由浏览器决定。保存成功后的导航直接完成。离开时已经发出的保存请求仍可能在服务器完成，因此重新打开时要以服务端内容为准；本章不承诺本地持久草稿。

5. 验证公开行为 ​

bash
node scripts/test-backend.mjs --test knowledge
pnpm exec vitest run apps/web/src/knowledge.test.tsx apps/web/src/design-system.test.tsx
just check

HTTP 测试通过真实 PostgreSQL 锁协调两个并发请求，确认一个成功、一个 409，随后从读取接口验证最终正文；还验证 Reader/不可见文档拒绝和审计失败回滚。View 测试验证宽屏双栏与实时预览、跨断点草稿与模式保留、窄屏页签键盘切换、保存中禁用、后台刷新不丢草稿、冲突读取与显式恢复、取消离开保留输入。设计系统测试验证“保存冲突与草稿保护”场景的四种反馈：成功、失败、版本冲突、权限失效——失败警告带请求编号，冲突读取最新版本后“放弃草稿”（正文换成最新内容）与“保留草稿”两条出路都能走到成功状态，全部是演示数据。

关键旅程完成后集中运行：

bash
node scripts/e2e.mjs tests/e2e/knowledge.spec.ts

第一个旅程断言桌面宽度的双栏布局、实时预览，再把视口缩窄验证页签模式；第二个场景用两个真实标签页制造冲突，人工合并后从另一页刷新确认版本 3。日常修改继续使用定向 HTTP/View 测试。

6. 应用于自己的业务 ​

任何可能被两个人修改的记录都可以携带版本：表单记住读取时的 version，服务端在授权事务内条件更新，客户端在 409 后保留输入并展示恢复选择。不要在 Controller 里“先 SELECT 再无条件 UPDATE”，也不要每次后台刷新都把服务器对象复制进表单。

编辑器的保存反馈可以按同一通道进入设计系统展厅：示例在自己的 contribution 里声明 scenes（标题、描述与可选的渲染体），程序集负责命名空间与双语校验。场景只用演示数据与局部状态，不复刻业务写入。

本章编辑 Views、Web 接线、API、合同类型、测试与教程都归知识库示例。所有权清单登记这些入口；通用 AlertDialog 留在 UI 包，可由下一种业务复用。
